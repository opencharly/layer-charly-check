# 2026.287.2203 — docs(check): state the context mapping once, and drop the inert `context: [deploy]` from assert-kind steps

## Summary

`context: [deploy]` **on a `check:` step is active in NEITHER check mode**: the check engine
activates `build` under `charly check box` and `runtime` under `charly check live`. A step authored
that way is skipped in both modes — so a plan that relies on it **asserts nothing while the summary
reads green**, which is R7's *"a test that cannot fail is invalid"* reached from the other side: a
check that can never run.

This corpus was recommending the inert value for assert-kind steps in **66 places across 15 skills**
(`adb`, `appium`, `cdp`, `dbus`, `libvirt`, `spice`, `vnc`, `record`, `check`, and the shared
references), against **3 sentences that already stated the truth** — the `record` skill says,
correctly, *"author them with `context: [runtime]` … (`context: [deploy]` is skipped in live
mode)"*. **The corpus contradicted itself, and that internal contradiction is the defect**: it is why
the class reached `main` twice in shipped candies and why two skill references teach it.

Measured (org-wide scan, 1115 `charly.yml` manifests at depth ≤ 6, excluding `.build/` and the
session worktrees, parsed as YAML rather than grepped): only **5** assert-kind steps declare
`context: [deploy]` alone, of which **2 are real** (`plugin-kube`'s `kube-nodes-ready`,
`layer-examplestep-deploy-consumer`'s `examplestep-deploy-applied`), 3 are mirrors of ONE umbrella
task step (the `opencharly/opencharly#413` class — the task verb's grammar is permissive, so they
run), and 1 more carries `['build','deploy']` and is fine. **So this is a DOCUMENTATION-LED defect
with two live instances, not a systemic functional one** — and the documentation is the bigger half,
because it is what authors copy.

ONE cutover, `charly.yml` only (+74 / −73), all of it prose inside the skill entities — **no plan
step, no package, no service, no schema, no pin**:

* **the mapping is stated ONCE, authoritatively** — on the shared-modifiers `context:` row
  (`references/verb-catalog.md`'s source) and in the three-levels table: *the engine activates
  exactly `build` (box) and `runtime` (live); an unscoped plugin-envelope step runs in both;
  `deploy` is not a mode any check runner has — it names the install timeline on a `run:` step only;
  use `[runtime]` for a live-only assertion.* Both statements cite the authority and the issue.
* **55 `check:` / `agent-check:` examples moved `[deploy]` → `[runtime]`** (the live-container probe
  verbs: `cdp`, `wl`, `dbus`, `vnc`, `mcp`, `kube`, `record`, `spice`, `libvirt`, `adb`, `appium`,
  `jetkvm`, `console`, `cua`).
* **11 prose recommendations corrected** — `adb` (*"`context: [deploy]` only"*), `appium`, `cdp`,
  `dbus`, `libvirt`, `spice`, `vnc` (two places), the `authoring-gotchas` #9 example
  (`# ✓ context: [deploy] so it runs only against live containers`) and #12
  (*"Alternative: give the step `context: [deploy]` …"*), and `beds-and-r10`'s sentence
  *"author the step at `context: [deploy]`"* — the last of which the previous session's brief cited
  as the documented remedy for a build artifact, so it was load-bearing.
* **the 36 `run:`-step examples keep `[deploy]`** — meaningful there (the install timeline), and the
  R5 sweep below proves none of them moved.
* the **one** sentence that already stated the truth (`record`) is sharpened to name the authority,
  so the corpus's single correct instance becomes the reference rather than an outlier.
