# 2026.280.2247 — docs(check): the venue-teardown claim no longer reads as success-tail-only (plugin-check#75)

**Head `97dd8b545858cd0d1f2d41392dd3d03710d680e3`**

## Summary

`/charly-check:check`'s `beds-and-r10` reference is the sole owner of the R10 change-class matrix
**and** of the bed doctrine. One sentence of that doctrine — the final paragraph of the bed-teardown
section, `charly.yml:2491` in this repo, `beds-and-r10.md:299` in the projection — read:

> Final target and member teardown are recorded acceptance steps.

That is true of the SUCCESS tail and false as a complete account of the behaviour. It was also the
whole of the reader's model of teardown, so a failing bed run looked like it had torn nothing down —
which is exactly the defect `opencharly/plugin-check#75` fixed: `cleanup` and `cleanup-members` were
the last two entries of the bed's own step list, so every earlier `return fail(...)` skipped them and
left the disposable target (for a VM bed, a whole booted guest) running.

**This is that fix's guidance surface, and it lands here rather than in the generated file.**
`layer-charly-check/charly.yml` is the SOURCE `skill:` entity; `charly marketplace generate` projects
it into `marketplace/check/skills/check/references/beds-and-r10.md` and `charly docs generate` renders
that onto opencharly.ai. Editing the generated copy is forbidden and would be reverted; the source is
the only correct home.

**The replacement is `teardown`'s measured proposal**, taken verbatim from that session's
`opencharly/plugin-check#89` body (its own greps are against the projection), and it states the
behaviour the merged code now has:

* teardown happens on the **success tail** as recorded acceptance steps (a targetless group records
  `cleanup-members`);
* **and** on **every unwinding failure path** through the bed runner's ONE venue-teardown owner — a
  failed run disposes of its deployed target and its members unless retention was explicitly
  requested (`--keep-on-failure`, `--keep`/`--keep-venue`, `keep_venue:`, or the root's
  `ephemeral.keep_on_failure:`);
* on the success path a failed members-down operation fails the bed; on the failure path it is
  reported as a **warning**, so the original step error survives;
* the **signal path cannot tear down at all** (nothing unwinds), so `charly check stop` names the
  scoped destroy verb instead.

The group fresh-rebuild sentence that followed is preserved unchanged — it states a different
transition and nothing in `#75` touches it.

**Not a T4 marker change, stated for the record.** This edit moves no criterion the validator
applies and weakens no marker; it is doctrine prose whose statement the merged code fix already made
false. Compare `opencharly/layer-charly-check#33`, which *did* change the probe the validator uses
and carried an operator sign-off for it: this one changes no probe, no `FORBIDDEN_*` list and no gate
condition.
