# 2026.242.2148 — docs(check): the shared-modifiers table omits eventually: and retry_interval:

## Summary

The `check` skill's **Shared modifiers** table lists `id`, `description`, `skip`,
`exclude_distro`, `timeout` and `context` — and omits **`eventually:`** and
**`retry_interval:`**, which are the only sanctioned way to wait for anything in a check
step.

The consequence is not cosmetic. Reading the skill as the reference it claims to be leads
to the conclusion that charly cannot poll, and therefore that any assertion about
something which takes time to come up must either be raced or preceded by a sleep. Sleeps
are an R4 violation, so a reader who believes there is no polling has no correct option
left — they either write a flaky check or a rule-breaking one.

I hit exactly this while porting upstream Omarchy's acceptance suite, which uses a polling
helper 57 times. The skill said there was no such modifier; the schema had carried one all
along.

Both fields have existed for a long time (`spec/schema/_common.cue:118-119`, implemented in
`sdk/kit/eventually.go`), and this same skill already **uses** `eventually:` twice in worked
examples further down. It was simply never added to the table a reader consults to find out
what a step can carry.

The two new rows document the semantics that actually matter when authoring:

- the **first pass wins** and returns immediately, so a fast success is not delayed;
- on failure the **last attempt** is reported, annotated `(after N attempts over D)`, so the
  failure text is the real one rather than a truncated first try;
- **absent means the handler runs exactly once** — which is precisely why adding the field
  is what turns a racy check into a deterministic one;
- `retry_interval:` defaults to 1s and is clamped if it exceeds the deadline.

No behaviour change: this is the corpus catching up with the schema.
