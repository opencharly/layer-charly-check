# 2026.330.1214 — docs(cdp): document `cdp: axtree` and route recovery through the supervised browser

## Summary

Two fixes to the `cdp` skill (owned by this repo's `charly-check` candy). Both are documentation
against a real product surface: the serving code at its pinned version is the source of every claim
here, and the parsed method list is pasted below.

- **`cdp: axtree` is documented.** The Quick Reference table omitted it, although `candy/plugin-cdp`
  serves it — `methods.go:77` declares it takes `tab`, `methods.go:134` dispatches it,
  `schema/cdp.cue:111` defines it — and the check skill's own `references/live-probe-verbs.md`
  allowlist already listed it. A reader looking for the page-structure query found no method. Added
  the table row plus a short method section with a runnable example, stating that what the tree
  contains tracks the browser's own accessibility state (so an image asserts what a run prints).
- **The recovery hint no longer starts a second browser.** It told an operator to relaunch Chrome
  with a `wl: exec` step running `chrome-wrapper`. On a supervised pod (`selkies-core`, and every
  KDE pod) that starts a SECOND browser beside the supervised one on the same `--user-data-dir`,
  and the wrapper's Singleton-lock cleanup hides the collision instead of reporting it; on a
  nested-KDE pod it also lands on the wrong display, because a compositor-driven launch inherits
  that compositor's socket (sway's `wayland-0`, behind the fullscreen Plasma window) instead of the
  session's (`wayland-kde`). It now names the one owner first (`supervisorctl restart chrome` / the
  `charly service restart` surface), falls back to a direct `chrome-wrapper` launch on the ambient
  display only when nothing supervises the browser, and says why neither bare `swaymsg` nor a
  compositor-specific launch step is the way in.
