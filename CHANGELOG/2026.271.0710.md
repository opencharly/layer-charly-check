# 2026.271.0710 — docs(skill): document host orchestration in a bed (check: steps, not a candy run:)

## Summary

Clarify the `/charly-check:check` skill with the **host-orchestration in a bed** rule — where a bed's HOST mutation (build a VM, bake a disk, push an image) belongs, so the shape is stated once instead of rediscovered per bed.

Added a subsection **"Host orchestration in a bed — author it in the bed's own `check:` step"** with these bullets:

- **A bed's own `run:` step is verify-only (skipped)** — so the mutation cannot live in the bed's `plan:` as a `run:`.
- **The bed's `check:` step is where the active binary is available.** The runner executes a bed's `check:` step on the venue (a `host: local` bed → the host), and the runtime check-var resolver stamps `${CHARLY_BIN}` with the active binary — so `${CHARLY_BIN}` drives the binary under test, not a stale PATH selection. This is the ONE place to author host orchestration, with a worked `host: local` bed example.
- **`timeout:` is MANDATORY for any step longer than the never-hang ceiling (~120s)** — a VM build/bake far exceeds it; without an explicit `timeout:` the probe is killed (`probe killed by never-hang ceiling`).
- **The step runs at BOTH `deploy-add` AND `check-live`, so it MUST be idempotent** (reuse a running registry, capture a golden once, tolerate a pre-existing domain).
- **Destroy only a `disposable: true` DEPLOY's domain** (`--domain`), never the shared `kind: vm` entity — cross-refs `/charly-vm:vm` "Disposability".

That is the complete, shipped diff. The `check:`-step-with-`${CHARLY_BIN}` form is the **source-grounded contract** (see How tested), not a defect framing.
